# 连接测试被误取消 · 修复记录

日期：2026-11-01。此处处理连接测试故障，没有修改时间制度或游戏规则。

## 原因与复现

手机从菜单打开设置时，openDialog 会先关闭菜单，再用同一个原生 dialog 展示设置。菜单的 close 事件异步到达；原设置页对 dialog 注册的一次性 close 监听把它当成设置关闭，提前中止了整页复用的 AbortController。后续测试拿到已取消的 signal，尚未 fetch 就返回“请求已取消”。

在独立localhost模拟接口中，按手机入口复现同样提示；服务端请求记录为空。用户截图中的密钥没有读取、复制或用于测试。原统计标题也只在打开设置时渲染，即使有请求完成也不实时更新，不能仅凭截图里的0次推断服务商是否收到请求。

## 修改

- 新增窗口请求作用域，以当前表单是否仍属于打开的 dialog 判断退出，忽略上一层窗口延迟到达的close。
- 每次测试使用独立AbortController；真正关闭或替换设置页才取消旧请求。旧窗口的结果 / finally 不写入新窗口。
- 测试期间禁用表单及保存按钮，避免连续点按或修改配置使结果与当前参数混淆；窗口关闭按钮仍可使用。
- 请求统计实时更新，并复用已有统计保存逻辑，刷新后可查。记录仍不含密钥、地址、正文或请求体。
- 区分密钥未通过、费用 / 权限、型号 / 地址、限流、服务端、网络和超时提示，不透传服务商响应正文。
- 批折的响应式清理监听存在相同的共用dialog事件风险，一并改为同一退出判断；手机 / 桌面切换后“选折”仍正常归位。

只修改src/ui、新增回归测试并重新生成index.html。src/core、src/llm、src/store及存档结构不变。

## 验证

- **125 / 125测试通过**，新增7项涵盖旧close事件、真正取消、不重试、窗口替换、独立信号、失效窗口与错误提示。
- 应用内浏览器390px路径：菜单首次测试成功、同窗连续测试成功；挂起请求关闭后重新打开测试成功；模拟HTTP401显示密钥验证提示；统计刷新保留。
- 1280px设置直达入口测试成功；从行动抽屉进入批折，390→1280→390后选折位置依次正确。
- 所有网络验收使用本地模拟Chat Completions / SSE和占位测试密钥，包括思考开关开启的请求，没有声称真实DeepSeek账户联调成功。
- 原故障服务端收到0次请求；修复后实际收到成功请求及一次真正关闭产生的中止，重复测试没有误取消。浏览器控制台未观察到error / warn。
- 200年 / 7,200旬模拟与修复前28字段一致；游戏、存档和既有接口参数不变。

原始截图、模拟接口记录与浏览器路径留在本机qa/probe-*；可复现的7项回归测试随仓库发布。Pages发布后会以缓存破除请求比对线上单文件SHA-256，线上只开关菜单 / 设置，不读取真实密钥、不提交游戏进度。

## 服务商核对

核对DeepSeek[官方型号说明](https://api-docs.deepseek.com/quick_start/pricing/)与[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)：当前推荐名称是deepseek-flash，但官方明确仍接受deepseek-v4-flash这个旧名称；thinking开关及JSON输出参数也受支持。本次保留用户已有型号和接口配置，没有把旧型号当成本条取消报错的原因。
