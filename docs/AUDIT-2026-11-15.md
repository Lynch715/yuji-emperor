## 一、口谕：三处断点，叠加起来等于"基本没实现"

### P0-1　口谕框大多数内容被直接丢弃
`src/ui/app.js` `oral()`（约 705 行）只认 14 个关键词（赈灾/减赋/修河…）。没命中时：
- 试读模式：直接 `chooseAction('下旨')` 打开空白下旨面板，玩家写的字**全部丢失**（`#edict-text` 为空）。
- 接 API 时：先发一次分类请求（`classifyMessages`），拿到 `kind` 后同样打开对应面板，文字照样丢失。

线上实测四条口谕：
| 输入 | 结果 |
|---|---|
| 赐死丞相 | 弹出空白下旨面板，文字丢失 |
| 命户部严查贪腐 | 同上 |
| 派兵北伐 | 同上 |
| 拨银十万两赈济灾民 | 生成「下旨·赈灾」卡（见下一条，实际无效） |

而真正能解析赐死、任免、拨款、宣战的意图系统（`intentInputs` → `requestScheduleIntents` → `resolveIntents`）只读取 **`下旨` 卡上的 `text`**。`oral()` 从不把文字放进卡里，所以口谕框根本进不了这套系统。

### P0-2　命中关键词的口谕也不生效
`oral()` 命中关键词时生成 `{kind:'下旨', edictType:'赈灾', text}`。但 `src/core/turn.js` 约 252 行：
```js
} else if (action.kind === "下旨") {
  const playerActions=intents.filter(a=>a.slot===slot);
  if(playerActions.length){ ...resolveIntents...; continue; }   // ← 跳过 issueEdict
  result = issueEdict(s, action, die);
```
只要卡上有文字，就一定会产生至少一个意图（`localIntents` 兜底推一个 `other`），于是 `issueEdict` 永远被跳过。`other` 只记成"拟议：xxx"，没有任何结算。

Node 复现（三档自由度结果相同）：
```
赈济直隶   | 口谕路径 赈灾项目 0，国库不动 | 面板路径 项目 1，国库 −30
修河       | 口谕路径 0                  | 面板路径 1
整饬吏治   | 口谕路径 0                  | 面板路径 1
减赋       | 口谕路径 0                  | 面板路径 1
```
"言出法随"档同样无效。在下旨面板里选了政令、再在附言里写一句"着有司速办"，也会触发同样的问题：政令被吞掉。

### P0-3　"拨银十万两赈济灾民"＝白扔十万两
`localIntents` 把它解析成 `allocate → destination:'政务'`（只认"修河"一个政令名），钱从国库扣掉，但不会开赈灾项目，也没有任何效果。线上实测国库 480 → 465，正文只写"拨银 10 万两"。
`resolveIntents` 其实支持 `destination` 为政令名时自动建项目，只是本地解析器没把"赈济/救灾/修河/整饬"等词映射成对应的 `EDICTS` 键。API 模式下能不能对上，完全看模型有没有正好返回 `decree` 或正确的 destination。

### 修复建议（按顺序）
1. **`oral()` 改成纯投递**：不再猜类型、不再发分类请求。永远生成 `{kind:'下旨', edictType: 猜到的类型或'禁令'占位, text}` 放进空槽，关闭对话框。解析统一留给起驾时的意图请求（一次合并调用，本来就有）。顺带省掉一次串行模型请求。
2. **`turn.js` 下旨分支**：如果本槽意图**全是 `other`**，且卡上有真实的 `edictType`（不是占位），照常 `issueEdict`；有实质意图（kill/appoint/allocate/decree…）时才走意图结算。另外要防止同一政令被意图和卡片重复执行（意图里已有同 edictType 的 decree 时跳过卡片）。
3. **`localIntents`**：关键词命中政令时直接产出 `decree`；`allocate` 的 destination 用同一张"词 → EDICTS 键"表（赈济/救灾→赈灾，治河/修堤→修河 …）。
4. **`intentMessages`**：把卡片上的 `edictType` 作为提示传给模型（"玩家已选政令：赈灾"），减少模型把它判成 other。
5. **补测试**：`oral()` 目前零覆盖。至少加：口谕文字进入卡片；"赈济X"生成赈灾项目；"赐死某人"在三档下的结果；"拨银N两赈灾"扣款并开项目。

## 二、卡顿：引擎不慢，慢在"等模型＋没反馈"

### 实测（桌面，试读档）
- 起驾一旬：24–69 ms，25 旬内无 >50 ms 长任务。
- 打开下旨/召见等面板：同步约 9–30 ms。
- 引擎（Node，720 旬＝20 年）：预演 1.4–4.7 ms，提交约 1.5 ms，渲染 3–6 ms（HTML 约 25 KB），整档存盘 6→28 ms，随年份线性增长。
- 手机按 4–8 倍估算，单次操作约 0.1–0.3 秒，可感知但不至于"很卡"。

结论：**体感卡顿主要来自模型请求的等待，加上等待期间界面没有任何反应**。具体如下。

### P1-1　起驾后先"冻住"数秒
`advance()` 设了 `busy=true`，但第一次 `render()` 在意图解析**完成之后**（约 500 行）才调用。有自由文本（口谕、朱批附言、自拟情节）时，要先等完一整次模型往返，期间按钮不变灰、没有"正在解析旨意"提示，看起来像死机，玩家容易连点。
→ `busy=true` 之后立刻 `render()`，并显示阶段文字（解析旨意 → 撰写本旬 → 誊录奏文）。

### P1-2　意图解析失败＝整旬失败
`requestScheduleIntents` 使用 `maxAttempts:1`；失败时抛错，`advance` 直接 toast 退出，什么都没预演。模型偶尔回一次坏 JSON，玩家就得重新点起驾，再等一轮。
→ 失败时退回 `localIntents`（本地解析）继续推演，toast 提示"旨意按字面办理"。

### P1-3　召见每说一句＝两次串行请求
`startTalk` 每句先 `requestPlayerIntents`（等完），再 `callJSON(talkMessages)`（再等）。对话越多越拖。
→ 方案 A：先用本地规则判断，没有动作词（赐/拨/任/罢/斩/宣战…）就跳过意图请求；方案 B：两个请求并行发，意图结果回来后再校验对话。A 改动小、收益大。

### P1-4　口谕框本身的串行分类请求
见 P0-1：没命中关键词就先发一次分类请求，期间对话框还开着，「降旨」可以再点（会报"本旬正在续写"）。按修复建议 1 删掉这次请求即可。

### P2　次要项
- **整页重绘**：`render()` 每次都对 `#app` 整体 `innerHTML`，头像 `<img>` 每次重建，会重新解码、闪一下。可以只重绘日程区和侧栏，或保留已加载的图片节点。
- **中文网络字体**：Google Fonts 的 Noto Serif/Sans SC 共 7 个字重，按 unicode-range 切片，界面出现新字就补拉一片，然后重排一次。在手机上表现为文字"跳一下"；国内网络下 googleapis 基本连不上，只能等超时后用系统字体。建议减到 2 个字重，或默认用系统字体、在设置里开关网络字体。
- **存档**：每次操作后都会存档，耗时随年份增长（20 年约 28 ms）。现在不是瓶颈，长局或手机上会慢慢显出来。可以把 `validate(main)` 的完整校验改成只在读档和导出时做。

## 四、iPhone 上「拟口谕」抽屉向右溢出（玩家截图，2026-11-15 补）

现象：iPhone 上键盘弹出后，抽屉里的输入框和「降旨」按钮右侧被截掉，右上角关闭按钮 × 看不到。

排查：
- 模拟 375 和 393 宽度（Chromium 移动模拟）：抽屉宽度正好等于屏宽，输入框右沿 358px，没有任何元素横向超出，`scrollWidth` 等于视口宽度。**布局本身不溢出**，Chromium 复现不了。
- 按截图量字号：标题、标签、占位文字都比实际 CSS（18/13/16px）大约 1.1 倍，而且画面以左边为准放大。这是 **iOS 页面被放大（缩放）后的样子**，不是 CSS 宽度算错了：要么是 iOS 聚焦输入框时自动放大，要么是之前双指放大后没缩回去。iOS 放大之后不会自动缩回，右侧就一直被截掉。

修复建议：
1. `src/ui/shell.html` 的 viewport 加 `maximum-scale=1`：
   `width=device-width,initial-scale=1,maximum-scale=1,viewport-fit=cover,interactive-widget=resizes-content`
   iOS 10 以后，这个设置只禁止聚焦时自动放大，玩家仍然可以双指缩放，不影响无障碍。
2. 窄屏下所有 `input, select, textarea` 显式写 `font-size: max(16px, 1em)`，不要只靠 `font: inherit` 间接拿到 16px。以后谁改了继承链，聚焦放大就会回来。
3. 保险起见加上 `dialog.drawer { max-width: 100vw; }` 和 `html { -webkit-text-size-adjust: 100%; }`。
4. 验收：真机（Safari 和添加到主屏幕两种方式）打开拟口谕、召见输入、自拟情节、朱批附言四个输入框，键盘弹出前后都不能出现横向截断。
